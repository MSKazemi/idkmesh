# Getting Help with IDKMesh

IDKMesh is early, and questions are valuable signals about where the project is unclear.

## Where to ask

### I do not understand the project yet

Open a GitHub issue with a title such as `[Question] What does ... mean?` and explain what you already read and what remains unclear.

A question that reveals confusing documentation is a useful contribution.

### I have an idea

Use the proposal/community issue templates when available. Describe the problem before prescribing a complete solution.

### I found a bug

Use the bug report template and include the smallest reproducible example you can provide.

### I want to contribute but do not know where

Open a `[Contributor]` issue describing your interests and skills: coding, research, documentation, design, distributed systems, security, community building, domain knowledge, testing, or something else.

### I have a security vulnerability

Do **not** open a public issue. Follow [`SECURITY.md`](SECURITY.md).

### I have a conduct or safety concern

Do not post sensitive personal details in a public issue. Follow [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md).

## Response expectations

The project should aim to acknowledge newcomer questions and first contributions promptly, but IDKMesh is currently volunteer-run and cannot guarantee a response time.

As the community grows, we should publicly measure time-to-first-response and add a rotating community triage role rather than relying on one maintainer.

## Future community channels

GitHub Issues and Pull Requests are currently the canonical public asynchronous channels.

GitHub Discussions should be enabled when possible for open-ended Q&A, introductions, show-and-tell, and broad community discussion. Any additional chat/forum platform should complement, not replace, durable public decision records in the repository.
